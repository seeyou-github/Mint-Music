# 哔哩哔哩插件「作者主页加载作品」频繁 412 —— 差异分析与解决方案

> 对比对象
> - 出问题的插件：`D:\Download\猫头猫 哔哩哔哩 0.3.1-patched.js`（内部 `version: 0.3.9-patched`），运行在 Mint-Music（本仓库）的 MusicFree 适配层里
> - 正常工作的项目：`D:\Code\Flutter_PiliPlus`（Flutter，作者主页 → 投稿列表）
>
> 结论先行：**两者根本不在同一条取数路径上**。PiliPlus 的作者主页走的是 **App 接口**（`app.bilibili.com/x/v2/space/archive/cursor`，appkey 签名，不校验 buvid/WBI），插件走的是 **网页 WBI 接口**（`api.bilibili.com/x/space/wbi/arc/search`，边缘 WAF 采样）。网页接口的 412 是**概率性**的，补 header 只能降低概率、不能消除；换到 App 接口后实测 0 次 412。已给出可直接替换的补丁 `bilibili-0.3.10-patched.js`。

---

## 一、复现与量化（本机实测，非推测）

### 1.1 同一 IP、同一秒、同一身份，两条路径的对照

| 请求 | 结果 |
| --- | --- |
| App 接口 第 1 页 | `200 / code=0`，`count=243` |
| 网页 WBI 第 1 页 | **`HTTP 412`**（返回 HTML 风控页） |
| 网页 WBI 第 2 页 | `200 / code=0`，`count=243` |
| App 接口 第 1 页（第二次） | `200 / code=0` |

同一身份、相邻 1 秒内，网页接口一半 412 一半正常 → **这就是「频繁触发」而不是「必然失败」的原因**。

### 1.2 原版插件 vs 补丁（同一套 Node 环境，模拟 Mint-Music 的 axios 桥）

每轮调用：作者第 1/2/3 页 + 跳页第 5 页。

| 版本 | 3 轮共 12 次调用 | 单次耗时 |
| --- | --- | --- |
| `0.3.9-patched`（原版） | **3/12 失败**（3 轮各失败 1 次，失败点分别落在第 3 页 / 跳页 / 跳页） | 常见 1.9s（撞 412 后 `1.5s` 冷却重试） |
| `0.3.10-patched`（补丁） | **0/12 失败** | 130 ~ 430ms |

> 原版的失败集中在「更靠后的页」，且失败前一次请求往往耗时 ~1.9s（说明先撞了一次 412、冷却 1.5s 后重试才成功）——这正是用户感知到的「进入作者主页卡一下、有时直接报错」。补丁走 App 接口后，第 5 页正常返回 19 条、0 重复。

### 1.3 网页接口 412 的「概率性」实测（每变体换全新 buvid，各 4~5 次）

| 请求形态 | 结果 | 412 命中 |
| --- | --- | --- |
| 插件现状：仅 `buvid3` cookie + 精简头 + `accept-encoding: br` | 412 412 412 412 200 | **4/5** |
| 仅补 `buvid4` / `buvid_fp` / `CURRENT_FNVAL` | 200 412 412 200 | 2/4 |
| 仅补浏览器指纹头（`sec-ch-ua*`、`priority`、`cache-control`） | 200 200 200 412 | 1/4 |
| 插件现状（另一次采样） | 200 200 200 200 | 0/4 |
| 完整头 + 完整 cookie（`buvid4`+`buvid_fp`+`CURRENT_FNVAL`，且不带 `br`） | 200 ×5 | 0/5 |

**关键判断**：单点补 header 的收益不稳定（同一形态两次采样 0/4 与 4/5 都出现过），说明 412 由服务端**随机采样 + 身份信誉**共同决定。**不要指望靠调 header 根治**——这是把方案设计成「换接口为主、补指纹为辅」的直接依据。

### 1.4 顺带查出的两个真 Bug

| 问题 | 证据 | 影响 |
| --- | --- | --- |
| `accept-encoding` 声明了 `br`，但宿主解不了 brotli | `api.bilibili.com/x/space/wbi/arc/search` 在声明 `br` 时返回 `content-encoding: br`（实测 115 字节）；Mint-Music 的 JS 桥用 `dart:io HttpClient`（`js_engine_service.dart:38-46`），它只自动解 gzip | 即使不被 412，也会拿到乱码字节 → `res.code === undefined` → 报「投稿列表 undefined」 |
| 作者作品列表 `duration` 恒为 0 | 网页 `vlist` 项只有 `length: "08:42"` 字符串，`formatMedia` 读的是 `result.duration` | 列表时长全部显示 0；App 接口直接给 `duration: 702`（秒） |

## 二、差异全景

### 2.1 取数路径（决定性差异）

| 维度 | PiliPlus 作者主页 | 插件 `getArtistWorks` |
| --- | --- | --- |
| 接口 | `app.bilibili.com/x/v2/space/archive/cursor`<br/>`lib/http/api.dart:339` | `api.bilibili.com/x/space/wbi/arc/search`<br/>`fetchArtistWorksOnce`（原文件 378-430 行） |
| 调用点 | `lib/pages/member_video/controller.dart:119` → `MemberHttp.spaceArchive` | 直接 `axios.get` |
| 鉴权 | `appkey + ts + sign`（MD5）<br/>`lib/utils/app_sign.dart` | `w_rid`（WBI）+ `wts` + `dm_img_*` 指纹参数 |
| Cookie | **不发 cookie**（`account_mgr.dart:59-83`：`isApp` 分支只加 header 和签名） | `buvid3` + `bili_ticket` |
| 风控面 | App 网关，不参与网页 WAF 采样 | 网页边缘 WAF，会回 HTTP 412 |
| 分页 | `aid` 游标（`controller.dart:122-127`） | `pn` 页码，`ps=30` |
| 412 处理 | 代码里**没有任何 412 分支**（全仓 grep 只有 `-352` 的错误文案） | 1.5s 冷却 + 同身份重试一次 |

> PiliPlus 里确实也保留了网页版 `searchArchive`（`lib/http/member.dart:349`），但只挂在可选路由 `/videoWeb`（`lib/router/app_pages.dart:176`），**不是作者主页的默认路径**。

### 2.2 身份与指纹

| 维度 | PiliPlus | 插件 |
| --- | --- | --- |
| buvid3 | 本地生成（`id_utils.dart:72`），**登录账号随 cookieJar 持久化到 Hive** | 本地生成，仅存内存，**每次启动都是新设备** |
| buvid4 | 登录态 cookieJar 里有 | **从未获取** |
| 激活 | `Request.buvidActive()`（`init.dart:64`），每账号一次 | `activateBuvid()`，每进程一次 |
| 登录态 | 可带 `SESSDATA`（网页接口 412 概率大幅下降） | 永远匿名 |
| UA | App UA（`constants.dart:24`）或 `BrowserUa.pc`（`browser_ua.dart`） | PC Chrome 121 写死 |
| 浏览器指纹头 | `BrowserUa.pc` + referer + origin（`member.dart:380-384`） | 只有 `origin`/`referer`/`sec-fetch-*`，缺 `sec-ch-ua*`、`priority` |
| 压缩协商 | 自建 gzip/brotli 解码（`init.dart:344-351`，依赖 `package:brotli`） | 声明 `br` 但宿主只能解 gzip |

### 2.3 分页语义（迁移时必须知道）

App 接口不是页码分页，实测：

| 传参 | 结果 |
| --- | --- |
| `pn=2` | 与第 1 页**完全重复 20/20** → `pn` 被忽略 |
| `next=<上一页的 next_cursor>` | 仍然重复 20/20 → `next_cursor` 不能当 `next` 用 |
| `aid=<上一页最后一条的 param>` | 19 条，**重复 0** → 唯一有效游标 |
| `ps=30` | 仍返回 20 条 → **页大小上限 20** |

（PiliPlus 正是用 `aid` 游标：`controller.dart:123-127` 把 `data.item.last.param` 作为下一页的 `aid`。）

## 三、解决方案

### 方案 A（推荐，已实现）：`getArtistWorks` 改走 App 接口，网页接口降级为兜底

改动集中在插件一处，不动宿主。核心四点：

1. **主路径换接口**：`app.bilibili.com/x/v2/space/archive/cursor`，`appkey + ts + MD5(query+appsec)` 签名，不带 cookie。
2. **游标缓存**：按 `mid` 缓存「第 p 页之后该用的 aid」，正常顺序翻页零额外请求；跳页时逐页补齐（上限 20 页），补不齐则落网页兜底。
3. **网页兜底加固**：补齐 `buvid4`/`buvid_fp`/`CURRENT_FNVAL`、浏览器指纹头、去掉 `br`；412 时**换掉 buvid3 并重新激活**再重试一次（原版只换 ticket 不换 buvid，等于撞同一个黑名单窗口）。
4. **字段映射**：App 列表项 → MusicFree 媒体项，顺带修掉 `duration=0`，并把 `first_cid` 带下去（播放时省掉一次风控敏感的 `view` 请求）。

关键代码（完整实现见 `bilibili-0.3.10-patched.js`）：

```js
function appSign(params) {
  params.appkey = APP_KEY;                       // dfca71928277209b
  params.ts = String(Math.floor(Date.now() / 1000));
  const query = Object.keys(params).sort()
    .map((k) => `${encodeURIComponent(k)}=${encodeURIComponent(params[k])}`).join("&");
  params.sign = CryptoJs.MD5(query + APP_SEC).toString();
  return params;
}

async function fetchAppArcPage(mid, page, aid) {
  const params = {
    vmid: mid, ps: 20, order: "pubdate", qn: 80,
    build: 8430300, version: "8.43.0", mobi_app: "android", platform: "android",
    c_locale: "zh_CN", s_locale: "zh_CN", channel: "master",
    statistics: APP_STATISTICS,
  };
  if (aid) params.aid = String(aid);             // ← 游标，不是 pn
  const res = (await axios.get("https://app.bilibili.com/x/v2/space/archive/cursor", {
    headers: APP_BASE_HEADERS,                   // App UA + env/app-key/x-bili-aurora-zone
    params: appSign(params),
  })).data;
  // ...校验 code，记录 chain.aids[page] = items[last].param
  return { isEnd: res.data.has_next === false, data: items.map(formatAppMedia) };
}
```

**验证结果**（`verify-in-node.js`，真打接口，4 轮 × 4 次调用）：

```
第1页: 20 条 | isEnd=false | 重复=0 | 305ms
第2页: 19 条 | isEnd=false | 重复=0 | 157ms
第3页: 19 条 | isEnd=false | 重复=0 | 148ms
跳页第5页: 19 条, 重复=0
```

**兜底分支也已验证**：把 App 接口强制改成返回 `-404` 后，插件自动落到网页 WBI 接口，仍正常返回（30 条/页，`isEnd=false`），不会把用户卡死在错误页。

### 方案 B（宿主侧，建议一并做）：让插件能收 brotli

`lib/features/plugin/platform/js_engine_service.dart` 的 `_executeHttpRequest` 里，dio 只配置了 `IOHttpClientAdapter`，`dart:io` 只解 gzip。两条路选一条：

- 在 Dart 侧对 `content-encoding: br` 用 `package:brotli` 解压（PiliPlus 就是这么做的，`init.dart:344-351`）；或
- 在 JS 桥的 axios 适配层（`musicfree_runtime.js` 的 `__mfCreateAxios`）里，把 `accept-encoding` 统一改写为 `gzip, deflate`。

前者治本（其他插件也可能声明 br），后者改动更小。**注意**：这不是 412 的成因，但会让「看起来像 412 的解析失败」彻底消失。

### 方案 C（不推荐单用）：只补网页接口的指纹

见 §1.3：同一形态两次采样出现 0/4 与 4/5，收益不可控。只有在「App 接口被墙/失效」时才需要依赖它，因此补丁里把它做成兜底而不是主路径。

## 四、风险与回归清单

| 风险 | 说明 | 处理 |
| --- | --- | --- |
| appkey 失效 | `dfca71928277209b` 是 PiliPlus 当前在用的 Android key，B 站换 key 会一起挂 | 兜底走网页接口；插件 `version` 升到 0.3.10，方便后续热更 |
| 页大小从 30 → 20 | App 接口 `ps` 上限 20，作者页每页条数变少、翻页次数变多 | 与 MusicFree 的 `pageSize=20` 一致，实际更整齐；`isEnd` 用 `has_next` 判断，不会漏尾页 |
| 跳页成本 | 直接请求第 N 页需要补齐 1..N-1 的游标 | 补页上限 20，超出落网页兜底；正常顺序翻页零额外请求 |
| 内存 | `arcChains` 每 mid 一个数组 | 已加 200 条上限 + 最旧淘汰 |
| 充电专属判定 | 网页用 `is_charging_arc`，App 用 `is_ugcpay` | 已映射为 `vipExclusive`；若线上出现漏标，按 `badges`/`sub_title_icon` 补判 |
| 多 P 视频 | `first_cid` 只是第一 P | 与旧行为一致（旧代码走 `view` 拿到的也是第一 P 的 cid） |
| 首页 30→20 的重复请求 | 宿主 `collection_detail_page` 有按 id 去重 + 自动补齐逻辑 | 无需改动 |
